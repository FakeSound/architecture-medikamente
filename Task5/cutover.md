# Cutover-план миграции — Медикаменте

---

## 1. Выбор стратегии миграции

### Обоснование выбора: Parallel Run

Из трёх предложенных вариантов выбран **Parallel Run** — запуск старой и новой системы параллельно с постепенным переводом пользователей по доменам.

**Почему не High-level design:**
High-level design — это архитектурный подход, а не стратегия миграции. Он применяется на этапе проектирования и уже был реализован в Task 2 (C4 Container, Privacy by Design). Сам по себе он не описывает как переключить живую систему.

**Почему не Branch by abstraction:**
Branch by abstraction предполагает введение абстрактных интерфейсов поверх старого кода с постепенной заменой реализации. Это хорошо работает когда есть единая кодовая база. У Медикаменте монолит реализован в 1С и Excel — это не код, который можно рефакторить слой за слоем. Применить Branch by abstraction к файловой 1С технически невозможно.

**Почему Parallel Run:**

| Критерий | Аргумент |
|---|---|
| Медицинские данные | Недопустима потеря данных или простой. Parallel run позволяет в любой момент вернуться к работе в AS-IS без потери данных |
| Операционное требование | Врачи и администраторы не могут работать без доступа к данным пациентов в рабочие часы |
| Масштаб компании | 35 пользователей — синхронизация между системами управляема |
| Постепенная валидация | Каждый домен проверяется в реальной работе до отключения AS-IS |
| Управляемый откат | При проблеме пользователи просто возвращаются к Excel/1С — данные там актуальны благодаря синхронизатору |

**Ограничения выбранной стратегии:**
- Нужно написать синхронизатор для каждого домена — нетривиальная разработка, особенно для Excel (нет событий, только polling)
- В период параллельной работы данные живут в двух местах — риск расхождения
- Пользователи временно работают в двух системах — повышенная нагрузка на обучение

## 2. О сроках MVP

В описании проекта указан ориентир — MVP через пару месяцев: пациент самостоятельно записывается, администратор видит запись.

**MVP за 2 месяца технически достижим только в ограниченном виде.** За это время реально построить сервис записи с базовым интерфейсом для администратора и пациента. При этом Privacy by Design, шифрование, ABAC, интеграция с медкартами и соответствие 152-ФЗ в этот срок не войдут — система будет функциональной, но не соответствующей целевым требованиям безопасности.

Полноценная защищённая система достигается по завершении полного плана миграции (~13 месяцев). Это осознанный trade-off: либо быстрый функциональный MVP без гарантий безопасности, либо правильно выстроенная система с соблюдением всех требований.

## 3. Как работает синхронизация и откат

### Синхронизация данных

В AS-IS нет API — пользователи вводят данные руками в Excel или 1С. Нельзя перехватить запрос и направить его в новую систему. Вместо этого нужен фоновый **синхронизатор** для каждого домена.

```
Пользователь вводит данные в Excel / 1С
        ↓
Синхронизатор (polling каждые N секунд)
замечает изменение → копирует в PostgreSQL

Пользователь вводит данные в новый интерфейс МИС
        ↓
Синхронизатор копирует запись обратно в Excel / 1С
```

Для 1С синхронизатор реализуется через триггеры — при каждом сохранении 1С отправляет событие. Для Excel — только polling. Задержка синхронизации не должна превышать 1 минуту — это требование к разработке синхронизатора, а не просто мера по снижению риска.

### Особенность миграции EMR-документов

Для доменов Billing, Appointment, Patient синхронизатор работает с табличными данными. Для Medical (EMR) ситуация другая: медкарты хранятся как PDF/JPG-сканы на файловом диске.

**Файлы переносятся автоматически.** Если сканы организованы в папках по пациентам, перенос скриптуется: зашифровать каждый файл → загрузить в Object Storage → привязать к ID пациента в PostgreSQL. Это не ручная работа.

**Структурированные данные из сканов — отдельная история.** Если диагнозы нужны как поля в БД (для поиска, аналитики, ABAC), их нужно извлечь из PDF/JPG. Это возможно через OCR, но OCR даёт текст без структуры — непонятно где диагноз, где назначение, где анамнез. Ручная разметка ненадёжна при большом объёме, AI — ненадёжен по точности.

**Практический подход:** на старте переносить файлы как есть — врач открывает скан в МИС как раньше. Структурированные данные накапливаются естественно: каждый новый приём врач вводит уже в МИС структурированно. Это позволяет запустить Medical домен без блокирующей ручной работы по разметке.

Объём файлов нужно оценить до начала фазы 4.4 — это влияет на время выполнения pipeline.

### Dual-storage и 152-ФЗ

Во время parallel run одни и те же ПДн хранятся в двух местах: AS-IS (Excel/1С) и TO-BE (PostgreSQL). Формально — это два места обработки данных. Пациент давал согласие на обработку в одной системе, а синхронизатор копирует данные в другую.

До начала parallel run необходимо: юридически обосновать что синхронизация является технической миграцией в рамках той же цели обработки, а не новой обработкой данных — или предусмотреть обновлённое согласие. Эта задача назначается DPO/юристу на этапе подготовки.

### Откат

```
Проблема обнаружена в домене N
        ↓
Сотрудники возвращаются к Excel / 1С для домена N
(данные актуальны — синхронизатор всё время обновлял)
        ↓
Dev отключает интерфейс МИС для домена N
        ↓
Разбор инцидента (max 48 часов)
        ↓
Исправление → повторный запуск parallel run для домена N
```

Остальные домены не затрагиваются.

## 4. Роли и ответственность

| Роль | Описание | Ответственность |
|---|---|---|
| **PM** | Координация | Сроки, эскалация рисков, коммуникация |
| **Arch** | Технические решения | API-контракты, границы доменов, архитектура синхронизаторов, технические решения по безопасности |
| **DevOps/SRE** | Инфраструктура и надёжность | K8s, CI/CD, PostgreSQL, бэкапы; SLO/SLI, мониторинг, on-call, incident response |
| **Security-инженер** | Защита данных | Настройка TDE, KMS, mTLS; конфигурация OPA-политик; проверка audit log; penetration test перед Cutover day; консультация по 152-ФЗ |
| **Dev** | Разработка | Микросервисы, синхронизаторы, схемы БД, миграционные скрипты, EMR pipeline |
| **QA** | Качество | Тест-планы, UAT, нагрузочное и регрессионное тестирование, проверка синхронизации |
| **Business Owner** | Бизнес-приоритеты | UAT-подтверждение, go/no-go, обучение персонала |
| **IT Admin** | Текущая инфраструктура | Поддержка AS-IS во время параллельного периода; обеспечение read-only режима AS-IS после перехода каждого домена |

## 6. Go/no-go критерии

Переход к следующему домену только при выполнении обоих условий:
- Нет критических инцидентов за последние 5 рабочих дней
- Сверка агрегатов между МИС и AS-IS не выявила расхождений: количество записей совпадает, суммы платежей совпадают, список пациентов совпадает

## 7. Ключевые решения

| Решение | Обоснование |
|---|---|
| MVP за 2 месяца — только сервис записи, без Privacy by Design | Честный trade-off: функциональность vs безопасность. Полная система требует ~13 месяцев |
| Maintenance window воскресенье 23:00–03:00 | Минимальная нагрузка; клиника скорее всего не принимает пациентов ночью в выходные |
| Excel/1С → read-only сразу после перехода домена | IT Admin отвечает за этот шаг; устраняет двойной ввод и конфликты синхронизации |
| AS-IS на чтение 4 недели под контролем IT Admin | Страховка для исторического контекста; IT Admin гарантирует что никто не пишет в AS-IS |
| EMR pipeline — отдельная оценка до начала фазы 4.4 | Объём ручной работы по разметке файлов неизвестен; без оценки риск сдвига сроков критический |
| Dual-storage/152-ФЗ — задача для DPO на этапе 0 | Юридический вопрос должен быть закрыт до начала parallel run |
