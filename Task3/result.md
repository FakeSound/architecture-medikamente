# Задание 3. Стратегия защиты данных — Шифрование at Rest и In Transit

---

## 1. Классификация данных

Классификация основана на тегах, определённых в Task 1. Каждый класс рассматривается в двух состояниях: **at rest** (хранение) и **in transit** (передача).

| Данные | Тег | Состояние | Вероятность утечки | Ущерб | Уровень риска |
|---|---|---|---|---|---|
| ФИО, дата рождения, телефон, email, адрес | `PII` | At rest + In transit | Высокая — хранятся в Excel без защиты | Высокий — штраф по 152-ФЗ, репутационный ущерб | 🟠 High |
| Диагнозы, назначения, анализы, медкарты | `MEDICAL` | At rest + In transit | Средняя — требует доступа к серверу | Критический — медицинская тайна, ст. 10 152-ФЗ, невозможность отзыва | 🔴 Critical |
| Суммы платежей, вид услуги, фискальные данные | `FINANCIAL` | At rest + In transit | Средняя — 1С без шифрования | Высокий — финансовое мошенничество, налоговые риски | 🟠 High |
| Данные в канале клиент ↔ API Gateway | Все теги | In transit | Средняя — MITM в публичных сетях | Критический — перехват всех категорий данных | 🔴 Critical |
| Данные в канале система ↔ лаборатория | `MEDICAL` | In transit | Низкая — внешний канал с контролируемой стороной | Высокий — передача мед. данных третьей стороне | 🟠 High |
| Резервные копии БД | Все теги | At rest | Низкая — физический доступ к серверу | Критический — полная компрометация всех данных | 🟠 High |

## 2. Данные, необходимость защиты и инструменты

| Данные | В чём необходимость защиты | Инструменты защиты |
|---|---|---|
| Карточки пациентов (ФИО, контакты, адрес) | Хранятся в СУБД. Компрометация БД даёт прямой доступ к ПДн | TDE на уровне PostgreSQL |
| Медицинские карты (диагнозы, анализы) | Специальная категория ПДн по ст. 10 152-ФЗ. Хранятся как файлы — без шифрования уязвимы при физическом доступе | AES-256 для файлов в Object Storage; TDE для структурированных данных в СУБД |
| Финансовые данные (платежи, чеки) | 1С в файловом режиме не шифрует данные. Доступ к файлам даёт доступ к финансовой истории | TDE при переводе 1С на клиент-серверный режим с PostgreSQL |
| Трафик клиент ↔ API Gateway | Без шифрования канала ПДн передаются в открытом виде. Уязвимость к MITM-атакам | TLS 1.3 на всех входящих соединениях; HSTS для веб-клиентов |
| Трафик между внутренними сервисами | Внутренний трафик может быть перехвачен при компрометации сети | TLS 1.3 для межсервисного взаимодействия; mTLS для критичных каналов |
| Трафик система ↔ лаборатория | Медицинские данные передаются третьей стороне. Канал должен быть защищён и аутентифицирован | mTLS; передача только токена пациента через Vault, без ФИО |
| Резервные копии | Кража носителя или физический доступ к серверу = полная компрометация | AES-256 для резервных копий; ключи в KMS; offsite хранение |
| Ключи шифрования | Если ключи рядом с данными — шифрование бессмысленно | KMS (HashiCorp Vault); HSM для master keys |

## 3. Шифрование at Rest

### Применение по компонентам

| Компонент | Данные | Метод | Уровень |
|---|---|---|---|
| PostgreSQL | PII, MEDICAL, FINANCIAL | TDE (Transparent Data Encryption) | Весь файл данных БД |
| Object Storage | Медкарты (PDF/JPG), сканы документов | Server-side encryption AES-256 | Каждый объект |
| Резервные копии | Полный дамп БД и файлов | AES-256 перед записью на носитель | Файл бэкапа |
| Ключи шифрования | Master keys, Data Encryption Keys | KMS / HSM | Защищённый модуль |


> **Примечание — резервные копии:** бэкап на том же физическом сервере не защищает от кражи оборудования или пожара. Необходимо offsite хранение — минимум одна копия на внешнем носителе или в изолированном облачном хранилище, физически отделённом от основного сервера.

### Шифрование in Use (осознанное исключение)

В классической модели выделяют три состояния данных: at rest, in transit и **in use** — когда данные находятся в памяти процесса при обработке. При открытии медкарты врачом данные расшифровываются в RAM приложения и потенциально уязвимы к атакам на память (memory dump).

Для полной защиты применяются Trusted Execution Environment (TEE) или application-level memory protection. Для текущего масштаба Медикаменте эти меры избыточны и явно исключаются из стратегии. При росте до нескольких филиалов и увеличении числа пользователей этот вопрос стоит пересмотреть.

### Иерархия ключей

```
Master Key (хранится в HSM / KMS)
  └── Data Encryption Key (DEK) — для каждой таблицы / бакета
        └── Данные зашифрованы DEK
```

Если DEK скомпрометирован — перешифровывается только он, без повторного шифрования всех данных. Master Key никогда не покидает KMS.

## 4. Шифрование In Transit

### Карта соединений и применяемый протокол

| Соединение | Протокол | Аутентификация | Примечание |
|---|---|---|---|
| Браузер / мобильное приложение → API Gateway | TLS 1.3 | Сертификат сервера | HSTS; TLS 1.3 — минимум для новой системы |
| API Gateway → IAM / SSO | TLS 1.3 | Сертификат сервера | Внутренняя сеть |
| API Gateway → Business Services | TLS 1.3 | mTLS | Взаимная аутентификация сервисов |
| Business Services → PostgreSQL | TLS 1.3 | Сертификат сервера | Зашифрованный канал к БД |
| Business Services → Object Storage | TLS 1.3 | Сертификат сервера | |
| Medical Service → Vault | mTLS | Взаимная | Токенизация ПДн перед передачей в лабораторию |
| Vault → Lab System | mTLS | Взаимная | Внешний канал; только токен без ФИО |
| Billing Service → 1С | TLS 1.3 | Сертификат сервера | Финансовые данные |
| Billing Service → ККМ | TLS 1.3 | — | См. примечание ниже |
| Все сервисы → Audit Log Service | TLS 1.3 | mTLS | Целостность аудит-лога критична |

> **Примечание — ККМ и 54-ФЗ:** замена протокола взаимодействия с кассовым аппаратом затрагивает область, регулируемую приказами ФНС (форматы фискальных документов, протокол передачи данных ОФД). Перед реализацией необходимо проверить совместимость нового протокола с конкретной моделью ККМ у производителя и согласовать с оператором фискальных данных. Решение технически верно, но требует валидации до внедрения.

### Требования к TLS

Поскольку система проектируется с нуля, устанавливается **TLS 1.3 как минимально допустимая версия** для всех соединений.

- Запрещённые версии: SSL 3.0, TLS 1.0, TLS 1.1, TLS 1.2
- Допустимые cipher suites: `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`
- Сертификаты: срок действия не более 1 года; автоматическое обновление через ACME

## 5. Автоматизированный контроль

| Контроль | Что отслеживает | Инструмент | Действие при нарушении |
|---|---|---|---|
| Мониторинг сертификатов | Срок истечения TLS-сертификатов | Cert-manager / Prometheus | Алерт за 30/14/7 дней; автообновление через ACME |
| Ротация ключей шифрования | Возраст DEK | HashiCorp Vault | Автоматическая ротация по расписанию (раз в 90 дней) |
| Контроль cipher suites | Использование слабых алгоритмов | testssl.sh при деплое | Блокировка соединения; алерт |
| Контроль шифрования бэкапов | Наличие шифрования перед записью | Скрипт проверки | Отказ записи незашифрованного бэкапа |
| Контроль offsite бэкапов | Наличие актуальной копии вне сервера | Мониторинг задания бэкапа | Алерт при отсутствии свежей offsite копии |
| Сканирование открытых данных | ПДн в незашифрованных файлах | Data Classification Scanner | Алерт; карантин файла |
| Audit log доступа к ключам | Кто и когда запрашивал DEK | Vault audit log → SIEM | Алерт при нетипичном обращении |
| Policy enforcement | Соответствие конфигурации политикам | OPA (Open Policy Agent) | Блокировка деплоя при несоответствии |

## 6. Реестр программных и аппаратных средств защиты данных

### Программные средства

| Средство | Тип | Назначение | Применение |
|---|---|---|---|
| **HashiCorp Vault** | Программное | KMS — хранение и ротация ключей шифрования; токенизация ПДн | At rest: ключи для TDE и Object Storage; токенизация для лаборатории |
| **HashiCorp Vault Secrets** | Программное | Управление секретами приложений: пароли БД, API-ключи, connection strings | Все сервисы получают секреты из Vault, а не из конфигурационных файлов |
| **OpenSSL / BoringSSL** | Программное | TLS-библиотека для шифрования каналов | In transit: все соединения |
| **Cert-manager** | Программное | Автоматическое управление TLS-сертификатами | In transit: автообновление через ACME |
| **OPA (Open Policy Agent)** | Программное | Проверка политик шифрования при деплое | Автоматизированный контроль |
| **testssl.sh** | Программное | Сканирование конфигурации TLS | Автоматизированный контроль |
| **Prometheus + Alertmanager** | Программное | Мониторинг и алерты | Сертификаты, аномалии, offsite бэкапы |

### Аппаратные средства

| Средство | Тип | Назначение | Применение |
|---|---|---|---|
| **HSM (Hardware Security Module)** | Аппаратное | Хранение master keys в защищённом чипе; ключи не покидают устройство | At rest: защита master key |
