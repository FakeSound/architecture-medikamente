# Движок классификации данных — «Медикаменте»

---

## 1. Архитектурные принципы движка классификации

### Выбор технологического подхода
Согласно принципам проектирования, оптимальной стратегией классификации является **комбинированный подход**: автоматизированная система выполняет первичное распознавание и тегирование, а специалист по информационной безопасности (ИБ) осуществляет верификацию и корректировку неочевидных или спорных инцидентов.

Для обеспечения полного соответствия требованиям **ФЗ-152 РФ** (в части локализации баз данных и защиты специальных категорий ПДн), исключается использование зарубежных публичных облачных сервисов. Для реализации выбирается локальное программное обеспечение класса Data Governance и контроля защищенности данных, разворачиваемое внутри закрытого периметра компании (On-Premise) — например, решения уровня **Гарда Аналитика**, **Arenadata Catalog** или **Varonis (в локальной конфигурации)**.

### Компоненты платформы классификации (Уровень C2)

*   **Ingestion Gateway (Шлюз загрузки):** Точка входа для поступающей информации из систем-источников (PostgreSQL, файловый сервер, 1С, внешняя лаборатория) в пакетном или потоковом режимах. Направляет входящие потоки в промежуточный слой.
*   **Raw Landing (Слой первичного приема):** Изолированная зашифрованная область временного хранения данных до процедуры их анализа. Доступ к слою жестко ограничен и предоставляется исключительно служебным учетным записям ETL-конвейера.
*   **Classification Engine (Движок классификации):** Производит автоматизированное сканирование содержимого и структуры объектов. Назначает метаданные (теги) по двум стандартам:
    *   Категории конфиденциальности (Public, Internal, Confidential, Secret).
    *   Внутренние доменные теги системы: `PII` (Персональные данные), `MEDICAL` (Медицинские данные / Специальная категория ПДн по ст. 10 152-ФЗ), `FINANCIAL` (Финансовые данные).
    *   **Детектор изменений схем:** Контролирует консистентность структуры данных на входе. При изменении типов полей или появлении новых атрибутов движок автоматически инициирует повторный цикл классификации для измененных сущностей.
*   **Policy Decision Component (Модуль принятия политик):** На базе движка Open Policy Agent (OPA) сопоставляет назначенные теги с глобальными политиками безопасности и определяет дальнейший маршрут движения данных (в службу деанонимизации или в карантин).
*   **De-identification Service (Сервис деанонимизации):** Модуль трансформации данных (на базе Vault Transform Engine). Осуществляет динамическое маскирование, замену чувствительных атрибутов `PII` токенами и агрегацию медицинских показателей `MEDICAL` до требуемого уровня деперсонализации.
*   **Quarantine (Карантинная зона):** Изолированное хранилище для объектов, уровень уверенности автоматического классификатора по которым ниже установленного порога.
*   **Контур обратной связи (Feedback Loop):** Специалист по ИБ осуществляет ручной разбор объектов в карантинной зоне. На основе принятых решений актуализируются правила фильтрации в глобальном каталоге, что повышает точность последующих циклов автоматического анализа.
*   **Privacy & Data Governance Layer:** Единый централизованный компонент системы (**Data Catalog**), хранящий реестр тегов и политик доступа для всех смежных сервисов платформы.

## 2. Слои аналитического хранилища данных

| Слой хранения | Содержимое данных | Права доступа | Технологические меры защиты |
|---|---|---|---|
| **Raw Landing** | Необработанные данные до прохождения классификации | Исключительно служебные учетные записи конвейера (ETL) | Шифрование на уровне файловой системы (AES-256) |
| **Confidential Layer** | Структурированные данные с назначенными тегами, ПДн в исходном виде | Специалист по ИБ, Архитектор данных, служебные аккаунты загрузки | Прозрачное шифрование БД (TDE), ролевой доступ (RBAC), обязательный аудит обращений |
| **Pseudonymized Layer** | Медицинские данные, в которых прямые идентификаторы личности заменены токенами | Бизнес-аналитики, Data Scientist | Ограничение прав доступа (RBAC), прозрачное шифрование (TDE) |
| **Public / Aggregated Marts** | Деперсонализированные бизнес-метрики и агрегированные витрины | Конечные пользователи, BI-инструменты, аналитики | Разграничение прав доступа (RBAC) |

**Дополнительные механизмы управления доступом:**
*   **Row-Level Security (RLS):** Фильтрация строк на уровне СУБД. Позволяет разграничить видимость данных внутри Confidential Layer — аналитики конкретных филиалов получают доступ только к записям своего подразделения.
*   **Data Rights Management (DRM):** Программное ограничение операций выгрузки, копирования или локального сохранения информации пользователями аналитических панелей.
*   **Централизованный аудит:** Логирование всех фактов чтения и изменения данных в Confidential слое с передачей событий в Audit Log Service.

## 3. Метрики оценки эффективности классификации

### Метрики качества работы алгоритма
*   **Precision (Точность):** Доля объектов, корректно определенных как чувствительные, относительно общего объема данных, помеченных системой как конфиденциальные. Низкий показатель приводит к переполнению карантинной зоны.
*   **Recall (Полнота):** Доля чувствительных данных, которую алгоритм смог обнаружить, от общего реального объема конфиденциальной информации в батче. **Для медицинской системы МИС «Медикаменте» метрика Recall является приоритетной**, поскольку пропуск конфиденциальных данных (False Negative) несет регуляторные и юридические риски.
*   **F1-score:** Гармоническое среднее между точностью и полнотой, отражающее общий баланс качества классификации.

### Операционные и инфраструктурные метрики
*   **Объем карантинной зоны (Quarantine Rate):** Процентный объем данных, направляемый на ручную верификацию. Рост метрики сигнализирует о необходимости переобучения или изменения правил разметки.
*   **Покрытие классификации (Data Coverage):** Процентное отношение полей и таблиц, получивших валидный тег безопасности, к общему объему элементов в хранилище.
*   **Performance (Время обработки батча):** Длительность прохождения цикла классификации, используемая для планирования регламентных окон загрузки данных (ETL/ELT).

## 4. Обеспечение масштабируемости (Scalability)

*   **Горизонтальное масштабирование вычислительных мощностей:** Архитектура компонентов Classification Engine поддерживает независимое параллельное развертывание нескольких инстансов обработки. Нагрузка распределяется между узлами балансировщиком.
*   **Изоляция данных через партиционирование:** При масштабировании бизнеса и открытии новых филиалов применяется горизонтальное секционирование (партиционирование) таблиц хранилища по идентификатору филиала. Процесс классификации может выполняться изолированно для каждой партиции.
*   **Кэширование результатов структурного анализа:** Если схема данных источника (метаданные, типы полей, названия атрибутов) остается неизменной, Classification Engine использует сохраненный в кэше результат классификации для данной структуры. Повторный потоковый анализ содержимого применяется исключительно к неструктурированным текстовым полям (например, полям свободных комментариев).
*   **Единый реестр политик:** Использование централизованного компонента Data Catalog гарантирует, что любое изменение политик или добавление нового источника данных ИБ-инженером мгновенно применяется ко всем распределенным узлам платформы классификации без их перезапуска.
